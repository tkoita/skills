# IEEE フォーマット適合チェック

IEEE系の論文（主に `\documentclass[conference]{IEEEtran}`）が、**規則**（投稿先の規定と IEEEtran_HOWTO）と、**慣例**（IEEE自身の会議テンプレート、Reference Guide、数式ガイド、Author Center、Editorial Style Manual に書かれた書き方）に合っているかを調べ、指摘ごとに根拠を示して報告する。ファイルは書き換えない。直し方は案として示し、適用するかどうかはユーザーが決める。

## なぜこの手順なのか

体裁チェックでいちばん起きやすい失敗は、**言い過ぎ**である。「IEEEでは4人以上ならlong format」「キャプションは短くしなければならない」のように、ありもしない決まりや読み違えた決まりを断定してしまう。これを防ぐために、次の3つを守る。

- 根拠は必ず**原文を引用**し、出典と節番号を付ける。引用できないものは規則として扱わない。
- **誰の決まりか**を分ける。「投稿先の規定」「IEEEtran_HOWTO」「IEEEの慣例（会議テンプレートなど）」「論文誌向けの慣例」「好み」は重みが違う。投稿先が決めていないことは、はっきり「規定なし」と書く。
- IEEE の文書どうしも食い違うことがある（例：著者欄を所属でまとめるか。HOWTO はまとめ、会議テンプレートはまとめない）。片方だけを根拠に「間違い」と言わない。食い違いの扱いは `references/ieee-conventions.md` §2 に決めてある。
- 同じ研究室の採択論文なども、比べる材料としては役に立つ。ただし「採択された＝正しい」とは限らない。

## 手順

### 1. 対象を決める

- `.tex` と `.pdf` の両方があれば両方使う。`.tex` には行番号を付けて指摘できる。PDFからは、実際の見た目とフォントを確かめられる。
- 投稿先（会議名、ワークショップ名、トラック名。例：CANDAR'26 の WANC Short）と、段階（初回投稿かカメラレディか）を決める。ファイル名や `.tex` の中身から分かればそれを使う。分からなければ、ユーザーに一度だけ聞く。
- 比べる論文（例：同じ研究室の採択論文PDF）が渡されたら、同じ観点で並べて比べる。

### 2. 投稿先の規定を取りにいく

記憶に頼らず、WebSearch や WebFetch で公式ページを読む（CFP、Author Resources／Author Kit、ワークショップのページ）。取り出す項目は次のとおり。

- ページ数の上限・下限（トラック別）、用紙サイズ、指定テンプレート
- 匿名査読の有無、著作権表示（copyright notice）、PDF eXpress の要否
- AI利用の開示、カメラレディの締切と提出先

**書かれていない項目は「規定なし」と記録する。** 公式ページが読めなかったときは、読めなかったとそのまま書く。ここが分かるまでは、IEEEtran_HOWTO からの逸脱を「違反」と呼ばない。

公式ページを読むときは、次の点に注意する。

- 要約付きの WebFetch は、リンク先の中身や細かい数字を取りこぼすことがある。ページ数の上限や締切は、ページ本文から原文のまま拾う。DokuWiki で作られたサイト（URL が `/doku.php` や `/<page>` の形）は、`/_export/xhtml/<page>` や `/_export/raw/<page>` で本文だけを取り出せる。
- カメラレディの細かい指示（IEEE CPS の Author Kit、著作権表示、PDF eXpress の会議ID）は公開されず、採択通知のメールだけで届くことが多い。見つからなければ「公開ページには規定なし。採択通知で届く Author Kit を確認してほしい」と書く。
- 締切の日付も控えておき、今日の日付と比べる。締切は Author Resources や Schedule にあることが多い。要約で落ちやすいので、両方のページを見る。
- 「CPS（IEEE Computer Society）から出版される」というだけで compsoc 形式と決めない（「Figure」と書くか「Fig.」と書くかもこれで変わる）。投稿先か Author Kit が Computer Society 形式と書いているときだけ、そう扱う。

### 3. 機械的なチェックを走らせる

```bash
python3 "${CLAUDE_SKILL_DIR}/scripts/check_paper.py" --tex paper.tex --pdf paper.pdf
```

`${CLAUDE_SKILL_DIR}` はこのスキルのフォルダ（Claude Code が置き換える）。置き換わらない環境では、SKILL.md と同じフォルダの `scripts/check_paper.py` を指定する。必要なもの：python3（標準ライブラリだけで動く）と、PDFを調べるための poppler（`pdfinfo`、`pdffonts`、`pdftotext`、`pdfimages`、`pdftoppm`。Mac なら `brew install poppler`）。poppler がなければ PDF の検査を飛ばし、そのことを報告に書く。投稿先の規定を調べる手順2には、ネット検索（WebSearch／WebFetch）が要る。使えない環境では、規定を調べられなかったと書く。

`.tex` がなくPDFしかない論文（他人の採択論文など）でも、1ページ目の文字から著者欄の「1st」などの番号や、同じ所属の繰り返しを推定する。ただし精度は .tex より落ちるので、ページの画像で必ず確かめる。結果には「Facts」（クラスのオプション、著者欄の形、キャプションの語数、ページ数、用紙サイズ、フォント数）と「Candidates」（疑わしい箇所の候補）が出る。候補には次のレベルが付いている。

- check：誤りの可能性が高い
- warn：HOWTO からの逸脱
- info：判断が必要
- conv：IEEE の慣例からの逸脱（会議テンプレート、Reference Guide、数式ガイド、Author Center）
- ref：論文誌向けの慣例（Editorial Style Manual）。会議論文では参考

**候補はまだ結論ではない。** 次の手順で一つずつ確かめる。PDFの確認には poppler（`pdfinfo`、`pdffonts`、`pdfimages`）を使う。入っていなければ、その部分は飛ばされる。

### 4. 見た目を確かめる

スクリプトでは分からないことがあるので、PDFのページを画像にして見る（`pdftoppm -r 90 -png -f 1 -l N`）。最低限、次を確認する。

- 1ページ目の著者欄の見え方
- 表キャプションの行数（スモールキャップスの塊になっていないか）
- 図表が余白にはみ出していないか
- ページ番号やヘッダが出ていないか（会議モードでは出ない）
- 最終ページの左右の段がそろっているか

### 5. 一つずつ判定する

候補ごとに資料の該当する節を開き、原文に照らして判定する。規則（check／warn／info）は `references/ieeetran-rules.md`、慣例（conv／ref）は `references/ieee-conventions.md` を見る。著者欄とキャプションは読み違えやすいので、両方の資料の該当節を読む。判定は次の4段階に分ける。

| 区分 | 意味 | 例 |
|---|---|---|
| **A 規定違反** | 投稿先の規定に反する。または提出・掲載に響く | ページ数超過、フォント未埋め込み・Type 3 フォント、テンプレート文や仮の文字の残り、`\label` が `\caption` より前。投稿先が PDF eXpress を使うなら、IEEE Xplore の PDF 条件（リンクやブックマークなし、など）もここ |
| **B 規則からの逸脱** | 投稿先は決めていないが、IEEEtran_HOWTO の書き方と違う | 説明文が何文も入った表キャプション、表キャプションが表の下にある、禁止パッケージ、余白の調整 |
| **C 慣例からの逸脱** | IEEE 自身の会議テンプレート、Reference Guide、数式ガイド、Author Center の書き方と違う | 文中の「Figure 1」「Eq. (1)」「Ref. [3]」、略語を本文の初出で定義していない、「.25」、文献の会議名を略していない、本文中の式で分数を縦に積んでいる、サブタイトル |
| **D 参考・好み** | 論文誌向けの慣例（Editorial Style Manual）、または IEEE の文書どうしで割れている点 | 英国式の綴り、表キャプション末尾のピリオド、10以下の数を数字で書く、cite.sty による「[1]–[4]」の範囲表記、著者欄を所属でまとめるかどうか、「1st」「2nd」の番号 |

キャプションの長さだけを理由に指摘しない。IEEE のどの文書にも長さの決まりはない（`ieee-conventions.md` §8）。表キャプションに説明文が入っているときは「題名の形にして、説明は表の注へ」と提案し、図キャプションの長さには触れない。

誤検出は報告から外す。外した理由が大事なものは「問題なしと確認した項目」に一言だけ書く。

2つの資料に載っていない決まりや慣例を使いたくなったら、まず原典（HOWTO、投稿先のページ、IEEE の各ガイド）を取りにいき、引用できたときだけ使う。慣例は数が多いので、C と D は機械的な候補を全部並べず、まとまりごとに要約してよい（例：「英国式の綴りが18箇所（labelled、modelled ほか）」）。

### 6. 報告する

ユーザーには日本語で書く。専門用語には短い説明を添える。形式は次のとおり。

```markdown
## 結論
（1〜3行。提出前に直すべきもの（A）があるか、ないか）

## 投稿先の規定
| 項目 | 規定 | 出典 |
|---|---|---|
| ページ数 | WANC Short 4–5 pages | Author Resources |
| 著者欄の書き方 | 規定なし | — |

## 指摘（規則：A・B）
| 区分 | 場所 | 内容 | 根拠（原文の引用と出典） | 直し方の案 |
|---|---|---|---|---|
| A | paper.tex:42 | … | "…" (HOWTO §X-C) | … |

## 指摘（慣例：C・D）
| 区分 | 場所 | 内容 | 根拠（原文の引用と出典） | 直し方の案 |
|---|---|---|---|---|
| C | paper.tex:88 | 文中で「Figure~\ref」 | "Use the abbreviation 'Fig. 1', even at the beginning of a sentence." (IEEE conference template) | 「Fig.~\ref」にする |

## 問題なしと確認した項目
（短く。例：用紙はUS letter、フォントはすべて埋め込み済み、表キャプションは表の上）

## 確認できなかったこと
（読めなかった公式ページ、PDFがなくて調べられなかった点など）

Sources:
- [ページ名](URL)
```

- 「場所」は `.tex` の行番号、またはPDFのページ番号で書く。
- 2本の論文を比べたときは、「指摘」の前に観点ごとの比較表を入れる。
- ファイルは書き換えない。最後に「直すなら、どの指摘から適用するか」を聞いて終える。
- 締切が近いと分かったら、そのことも書く。
